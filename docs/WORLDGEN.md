# World generation

I mean clearly, the correct way to do this would be to create a data driven or programmable world generator.

## Definition
+ **Program**: per world terrain generator, contains everything.
+ **Phase**: **programs** are split into **phases**, where each phase only has access to the data generated by previous **phases**.
+ **Game state**: The world the player can access, interact with.
+ **Cache**: saved results from phases, to speed up world generation.

## Rules
+ The user should be able to decide what **program** to use.
+ The **program** doesn't have access to the **game state**, cannot read or write to it.
+ It can only access the **cache**.
+ If a **phase** needs data from a neighbouring chunk, look in the cache, or just regenerate that chunk, but only up to the previous phase.

## How?

Well, let's examine an example:

### Phase 1: Shaping
Sample 3D (with interpolation) separate solid from air (choose the data structure based on how this field is to be sampled). This creates the rough shape of the terrain.

### Phase 2: Carving
Caves. Sampling 3D noise.

### Phase 3: Foliage
Add grass, this is a rule where stone with air above it becomes grass. Below which is 2 layers of dirt. The checks might require cached/computed data from neighbours.

### Phase 4: Features
Find valid positions for trees, including in neighbouring chunks, then place all the blocks overlapping this chunk in this chunk.


Since the entire system is controlled/built using an api, I have to build a programmable world generator.
